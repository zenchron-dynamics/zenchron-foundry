## Authoritative post-merge sequence (PR #59)

Run in exactly this order. Steps 1-4 are the exact-commit CI evidence the seal
gate reads; steps 8-11 are the tag-first ceremony PR #59 introduced.

| # | Step | Note |
|---|------|------|
| 1 | Record the new `master` SHA | 40-hex, post-merge |
| 2 | Confirm `ci.yml` green on that SHA | runs automatically on push |
| 3 | **Dispatch `scan-images.yml` on that SHA** | no `push` trigger — must be dispatched |
| 4 | Confirm scan 10/10 green | attaches `scan <fam> <ver>` check-runs to that SHA |
| 5 | Dispatch `publish-rc.yml` on that exact SHA | typed `PUBLISH-<version>-<rc>-<SHA>` |
| 6 | **Record the publish-rc run ID** | sole source of the signed RC manifest |
| 7 | Verify the live RC from GHCR | `verify-rc.yml` |
| 8 | Create the stable tag on the same SHA | seals nothing; unlocks `foundry-production` |
| 9 | Dispatch `promote-stable.yml` **from the tag** | `PROMOTE-…` + `ACCEPT-RISK` |
| 10 | Verify stable aliases == RC manifest digests | 10/10 |
| 11 | Dispatch `release.yml` **from the same tag** with the RC run ID | seal |
| 12 | Verify the GitHub release assets | manifest, 10 SBOMs, checksums, evidence, VERIFY.md |
| 13 | Execute the rollback exercise | `scripts/rollback-stable.sh` |
| 14 | Restore the new release | re-promote, verify |
| 15 | Run final stable verification | 10/10 across the matrix |

Steps 3-4 are not optional: `scan-images.yml` has no `push` trigger, and the seal
gate requires its 10 check-runs on the exact release commit. Skipping them makes
step 11 refuse.

## Preconditions

- On `master`, clean tree, target commit merged.
- `REVISION` = `git rev-parse HEAD` (full 40-hex).
- Confirm the vuln-exception policy validates today (`scripts/validate-vulnerability-exceptions.sh`).

## 1. Publish RC (owner-triggered `publish-rc.yml`)

Inputs: `version=v2026.07.04`, `rc=rc1`, `expected_revision=<REVISION>`,
`confirmation=PUBLISH-v2026.07.04-rc1-<REVISION>`.
Produces immutable signed RC images + the signed RC manifest artifact
`rc-manifest-v2026.07.04-rc1`. Note the run ID.

## 2. Certify the RC (`verify-rc.yml`)

Inputs: `version`, `rc`, `expected_revision`. Must report cold build 10/10,
runtime smoke 10/10, contract 10/10, amd64+arm64 10/10.

## 3. Tag the release (BEFORE promotion)

`git tag v2026.07.04 <REVISION> && git push origin v2026.07.04`, on the exact
revision the RC was built from. The tag builds and seals nothing — it makes the
`foundry-production` environment (stable tags only) reachable and binds the
release to the commit.

## 4. Promote to stable (`promote-stable.yml`, **run from `refs/tags/v2026.07.04`**)

Inputs: `version`, `rc`, `rc_manifest_run_id=<step 1 run>`,
`expected_revision=<REVISION>`,
`confirmation=PROMOTE-v2026.07.04-<REVISION>`, `risk_acceptance_confirmation=ACCEPT-RISK`.
Two-phase, auto-rollback on failure. Keep the promotion evidence artifact.

## 5. Seal the release (`release.yml`, **run from the same tag**)

Dispatch with `version=v2026.07.04`, `rc`, `rc_manifest_run_id=<step 1 run>`.
The signed RC manifest is downloaded from that `publish-rc` run — **do not commit
it to `release-evidence/`**; that would move the tag off the RC revision and break
the equality chain. `release.yml` runs the exact-commit CI gate, fetches +
verifies the manifest, proves the stable aliases already hold the RC digests,
verifies all 10 stable images, builds + validates the evidence package, and
creates the GitHub release.

## Rollback

If promotion fails it self-rolls-back (reverse order) and uploads the incident.
If a sealed release must be pulled, see [rollback](../rollback.md).

## Abort criteria

Any gate REFUSE, any exit 99 (rollback incident), any manifest signature/binding
failure → stop, do not seal, investigate.
