## The seal failure (fourth live-only gate defect) and the lesson

The tagged `check-exact-commit-ci.sh` passed the full check-runs JSON to jq as
one argv argument. On the release commit that payload was 181,304 bytes across
57 check runs — over Linux `MAX_ARG_STRLEN` (131,072) — and it grows
monotonically with every verify/promote/seal run. The tag cannot move (seal
enforces tag commit == manifest revision), so the automated path was dead.
Predecessors: #59 (check names), #66 (guard permissions), and the v2026.07.04
`--argjson` JSON-glue crash.

**Standing rule:** dispatch `release-preflight.yml` against the candidate SHA
(a) before creating the tag and (b) again after verify-rc, when the check-runs
payload is at its largest. Both dispatches must be green before promotion.

## Dispatch gotchas (unchanged from v2026.07.04)

- `workflow_dispatch` takes a branch/tag ref, never a bare SHA: dispatch
  publish-rc with `--ref master` while master tip == RELEASE_REVISION
  (self-validated by `expected_revision`); promote/seal run from the tag.
- `scan-images.yml` has no inputs and does NOT self-validate — verify its run's
  `headSha` manually before counting it as evidence.
- Reruns keep the run ID (new attempt) and replay the ORIGINAL commit — a fix
  pushed mid-flight never reaches an in-flight run.
